# Performance

Design every read for the volume its data will have, and prove the speed with a number. Five steps, in order.

Fixing something slow? Time it now, before your first edit: step 5 needs that number. `devorb:debugging` finds the cause.

## 1. Volume and budget

For each table or list the work reads, write down rows and columns today and in a year, and the acceptable time. They come from the spec. With no number there, count the data that exists, or assume one, and record which you did.

With no budget in the request, the default applies: search under 200 ms at the server's p95; response to typing under 100 ms; INP under 200 ms.

**Small list.** A list that stays under about 1,000 rows in a year needs one thing: a limit on its query. Add the limit and stop here. Steps 2 to 5 are for volume, and a small list has none.

## 2. Where each read runs

The search lives where the data lives.

- **A server with a database:** search, filter and sort run in the database, through an index, and the route returns one page. A SQLite file behind a route is this case, at 20,000 rows as at 2 million.
- **The browser:** only when there is no server database to ask (static data, an offline app), or when the list is small and already whole on screen.

Loading the table once and keeping it in the server's memory, normalized, to filter there is the old scan with a cache in front. It measures fast today, and it still walks every row on every search, keeps a copy of the table in each process and pays the load again whenever the data changes. Put the normalized text in the database, behind an index, and let the query match the term.

## 3. The recipe

Read the reference for each decision the work has:

- `references/search.md`: rows are matched against typed text (a search box, a text filter).
- `references/reads.md`: a query lists, filters, sorts or loads related rows.
- `references/lists.md`: a screen draws more rows at once than fit in view.

Every read you touch leaves with none of these: a query with no limit; a query per row inside a loop (N+1); a filter or sort with no index; a list with neither pagination nor virtualization.

**Wide table** (more than about 12 columns). A list row is for recognizing a record, not for reading it, so a screen that draws every column is part of the slowness and no guide for the query. The list query returns the id, the few columns that tell a person which record this is and, in a search, the text that matched. The full row is read by id when a row is opened. With no one to say which columns identify a record, choose them from the data and name them in the report. A narrow table lists the columns it shows.

## 4. Write the budget down

In the spec, next to the volume. In every plan task that reads data, as the field `**Performance budget:**`, for example `**Performance budget:** search p95 under 200 ms at 60,000 rows × 85 columns`. A fix with no spec or plan states the budget in its report.

## 5. The proof

Fill the database to the real volume first: step 1's number, generated by a seeded script when the data does not exist yet. Two claims, each with its own measure:

- **"It got faster"** (a fix): the median before and the median after, measured as `devorb:verifying` says under Performance claims (5 alternating runs per side). The before number is the one you took before your first edit.
- **"It fits the budget"** (new work or a fix): at least 100 requests through the route, with varied real terms taken from the data (common, rare, absent, accented, short), and the p95 against the budget. Where the environment cannot open a port, time the function the route calls and say so.

Report one line per claim, each with its median or p95 and the number of runs behind it, and one line for the columns of a wide table. A range ("250 to 500 ms") is the spread: it follows the median, never replaces it.

```
Faster: search median 410 ms before, 3 ms after (5 alternating runs per side, spread 380–450 ms and 2–4 ms, 0 bad runs, 20,000 rows × 85 columns)
Budget: search p95 8 ms of 200 ms (100 requests, 40 distinct terms, search() called directly: no port in the sandbox)
Columns: the list returns id, name, city, code and the matched text, of 85; the full row loads by id. Chosen from the data: no one to ask
Not measured: response to typing, INP (no browser here)
```

## Connects to

- **Receives:** work that reads stored data, from `devorb:aligning` (volume and budget for the spec) and `devorb:planning` (the budget of each task); a slow screen or query whose cause `devorb:debugging` found.
- **Uses:** `references/search.md`, `references/reads.md`, `references/lists.md`.
- **Hands off to:** `devorb:verifying`, with the report lines and the commands behind them.
